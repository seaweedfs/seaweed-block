# v0.3.4 Alpha - Status Surface Hardening And Strict New-User Path

Status: alpha release note for the Phase 32 status-surface close and the
minimal new-user release validation. Runtime pods use the validated
`sha-6260e46fd3be` images; the documented uninstall path also requires the
repository-side cleanup script fix that scrubs iSCSI node DB records.

## Summary

Seaweed Block v0.3.4 alpha tightens the user-visible operations loop:

```text
Helm install
-> first PVC writer/reader verification
-> read-only report/dashboard/operator snapshot
-> negative-first status vocabulary
-> support-bundle replay using freshest evidence
-> strict uninstall and residue verification
```

This is still an alpha release. It is a stronger user walkthrough and
operations-evidence release, not a production operator or broad HA release.

## User-Visible Additions

- The documented new-user path now ends with strict cleanup verification.
- `scripts/uninstall-k8s-alpha.sh` scrubs Seaweed Block iSCSI node DB records,
  not only active iSCSI sessions.
- `sw-block ops report --from-bundle` prefers the freshest captured cluster
  evidence, so restart bundles do not replay an older primary when a newer
  post-restart snapshot exists.
- Status surfaces agree across `summary.txt`, `operator-snapshot.json`,
  dashboard JSON, dashboard HTML, explain output, and support bundles.
- Negative-first behavior is explicit:
  - ready evidence can show `Ready=True reason=first_volume_verified`;
  - known blockers show `Blocked=True reason=<stable_reason_code>`;
  - missing or stale evidence shows `Ready=Unknown` / `EvidenceStale=True`
    instead of a false ready claim.

## Current Claim

Seaweed Block v0.3.4 alpha may claim:

- Helm is the preferred alpha Kubernetes install path.
- A supported lab can run the documented path from install to first PVC,
  writer/reader verification, read-only report/dashboard, and clean uninstall.
- The read-only operations surface uses a shared ManagedVolume vocabulary.
- Blocked and stale evidence states are visible and do not falsely report
  ready.
- Support bundles can be replayed offline for report, explain, and dashboard.
- The documented cleanup path removes Kubernetes resources, active iSCSI
  sessions, Seaweed Block iSCSI node records, multipath/device-mapper residue,
  product processes, and hostPath residue.

These claims are tied to supported alpha labs and QA gates. They are not broad
production compatibility or availability commitments.

## Explicit Non-Claims

- Not production-ready.
- No production Kubernetes operator or controller-manager lifecycle.
- No mutating admin/operator/dashboard actions.
- No promote, repair, rebuild, failback, delete, backup, restore, or cleanup
  mutation through UI/API/operator.
- No backup/snapshot/restore workflow.
- No returned-replica rebuild or automated failback.
- No transparent Kubernetes node-loss failover without pod recreate.
- No NVMe ANA parity for the transparent failover path.
- No broad distro/kernel/initiator compatibility matrix.
- No broad upgrade/rollback safety beyond existing gated smoke paths.
- No performance, RTO, RPO, or SLO claim.

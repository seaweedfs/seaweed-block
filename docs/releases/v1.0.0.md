# v1.0.0

The first release. The supported configuration is the **single-replica volume** (`--durable-impl walstore-chunk`),
backed up to SeaweedFS with snapshots, restore, moves and volume delete. Replicated volumes ship as a preview: see
[replicated volumes in v1.0: a preview](replicated-volumes-preview.md).

## Store layout
- Chunks are named by their index and the SHA-256 of their bytes; manifests are per-shard segments and a root; HEAD
  names the current root and the named snapshots. Every name is derived from content, so an existing name is a
  complete object.
- Each volume has a random id. References carry ids, so a reference never resolves to another volume. The name of a
  deleted volume cannot be used again: create the replacement under another name.
- Each volume's store directory is `<name>-<first 8 hex digits of the volume id>` (for example `db1-3f9a2c7e`),
  created exclusively and never reused. Tools resolve a name to its directory only through blockmaster's volume
  record.
- Removal of unreachable objects is a conditional mark and then a conditional delete on the object itself, so a late
  delete never removes an object a newer image uses.

## Upgrade
- This is the first release. A store written by a pre-release build is refused at start
  (`chunkstore: legacy store format; recreate the volume`); there is no conversion. Recreate such volumes.
- No downgrade: a local data directory written by this release is refused by earlier builds.

## Durability and start-up
- Every read from the SeaweedFS store is checked against the chunk's content hash (guest reads, the first read of a
  restored volume's chunk, and restores); a damaged object is refused with a typed error, never served or installed.
- Extents are flushed only up to the acknowledged log position.
- blockvolume waits in-process while blockmaster is unreachable at start, and serves once blockmaster is back and its
  barrier has passed. A volume that was moved away or deleted exits 78; 75 means only that blockmaster could not be
  reached.
- A failed directory fsync after an authority record's rename stops blockmaster with exit 74; the restart reloads
  what is on disk.
- Empty local data at the holder's own epoch (a wrong or unmounted data directory) is refused with the cure named; a
  forced move records the lost range.

## Cleaning (on by default)
- The serving volume removes chunks that no snapshot or current image names: after each snapshot delete or retention
  pass, and every `--chunk-maintenance-interval` (default `1h`). Only the volume's holder cleans, never during a
  snapshot session; a cut or stop cancels a running cleaning.
- `--chunk-maintenance-gc=false` turns the cleaning off (retention still runs). SeaweedFS vacuum then reclaims the disk
  space of removed chunks.

## Authentication
- Control traffic that leaves the host is authenticated. One host: blockmaster's control API listens on loopback only,
  with no certificates; a non-loopback control listener without mutual TLS is refused at start. Several hosts: mutual
  TLS, with a fingerprint-pinned role file (viewer, operator, admin, node) and an audit log (`--audit-log`) of every
  operator and admin call.
- `--insecure-external-bind` and `--workspace-head-base-url` are removed: blockmaster refuses to start with either.
  blockmaster reads volume HEADs through its SeaweedFS filer connection (`--chunk-filer`).

## Limits
- Up to 10 snapshots per volume; one more is refused with `snapshot_limit` and changes nothing (delete a snapshot or
  let retention prune).
- Snapshot names up to 64 bytes; up to 4 labels per snapshot (keys up to 24 bytes, values up to 32 bytes).
- Up to 4 restore targets per snapshot and 16 per volume at a time.
- A volume's size, block size and chunk size are fixed at creation; resize is not supported, and a restore target
  always has its source's geometry.

## Not in this release
- Fork (a writable copy of a live volume): restore from a snapshot instead.
- `sw-block ops chunk gc`: removed; space is reclaimed by the volume's own cleaning, then SeaweedFS vacuum.
- Independent restore targets: a restored volume keeps reading its source's unchanged chunks, fetching each the first
  time the guest reads or writes it (there is no background fill). Its source snapshot, and the source volume, cannot
  be deleted while it depends on them: delete or release the restored volume first. A volume's plain snapshots, with
  no restored volume depending on them, are deleted with the volume.
- Authentication of the SeaweedFS links and of the volume process's loopback HTTP routes.

## Operator rules
- Do not edit or copy a volume's local data directory by hand.
- Run exactly one blockmaster per cluster; a second one on another host is not detected in this release.
- Never restore blockmaster's data directory from a backup or a copy: an older authority record reissues epochs that
  were already used. To recover, re-create the volumes from their snapshots.
- A delete right after a stop, or after a start or move that never served, is refused (`live until <T>`) until the
  lease horizon plus the clock-skew margin has passed (about a minute with default flags); then the same delete
  completes. Retry with the same request id; there is no bypass.

## Known limits
- If the outcome of a chunk upload is unknown (for example the connection drops mid-request), the object may remain in
  SeaweedFS unreferenced; the volume's cleaning does not reclaim it. `weed shell volume.fsck -collection <block
  collection> -v` lists such objects; do not use its delete option on block data.
- A restored volume takes no scheduled snapshots while any of its chunks is still only in the source snapshot (the
  pass is skipped as `restoring`). Read the whole device once if a restored volume must be backed up on schedule.
- A restored volume records which chunks it has fetched only at its next checkpoint: after a crash, chunks fetched
  since then are fetched again from the source snapshot (no data is lost).
- A snapshot of a restored volume cannot itself be a restore source (`restore_source_not_own`): restore chains are one
  level deep.
- blockmaster reads its cluster spec only at start: a new volume, restore target or host listed there takes effect
  after a blockmaster restart. A restart that blockmaster answers within about 10 s interrupts no serving volume; a
  longer one stops the holders (exit 75), which serve again at least about 50 s after blockmaster is back.
- A snapshot that meets a concurrent change of the volume's HEAD answers `head_conflict`: retry it. If that retry
  answers `internal` `snapshot "NAME" of VOL is not in HEAD after its commit`, retry once more; the data was committed
  either way, and the name is recorded only by the attempt that succeeds.
- A guest's NVMe/TCP connection to a target that stops waits, with the documented connect options, about 181 s before
  outstanding I/O fails when the holder process is stopped, and about 464 s when the host is powered off. A standalone
  guest runs on its volume's primary host (the target listens on loopback only). See
  [host connect settings](../operator-guide.md#host-connect-settings).
- Every deleted volume leaves one small record in blockmaster's deletion store, which keeps the name from being
  reused.

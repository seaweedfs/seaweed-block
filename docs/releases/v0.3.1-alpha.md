# v0.3.1 Alpha - Helm Lifecycle Hardening

## Summary

Seaweed Block v0.3.1 alpha hardens the v0.3 Helm-first Kubernetes path. The
release remains alpha, but the install loop now has gated evidence for chart
hygiene, a narrow upgrade/rollback smoke, multiple small PVCs, and cold
support-bundle replay.

The release boundary is:

```text
generate Helm values
-> helm install
-> first PVC and multiple PVC smoke
-> read-only report/dashboard/support bundle
-> one upgrade/rollback smoke with existing PVC data check
-> helm uninstall + host cleanup verification
```

## User-Visible Additions

- Helm chart hygiene gate: `helm lint`, `helm template`, chart package, and
  chart metadata are validated together.
- Narrow Helm lifecycle smoke: install, first PVC, upgrade, reader check,
  rollback, reader check, uninstall.
- Multi-volume Day-1 smoke: three PVCs bind, three writers verify data, three
  readers verify persisted bytes, and `sw-block ops report` lists three
  ManagedVolume rows.
- Support-bundle collector:

```bash
bash scripts/collect-helm-support-bundle.sh "$PWD"
```

It captures Helm metadata, Kubernetes snapshots, logs, iSCSI state, and
replayed read-only `sw-block ops report/explain/timeline --from-bundle`
artifacts.

## Current Claim

Seaweed Block v0.3.1 alpha provides a Helm-based Kubernetes alpha loop with
additional lifecycle confidence:

- chart renders and packages cleanly,
- one existing PVC survives a gated Helm upgrade/rollback smoke,
- a small three-PVC workload verifies writer/reader persistence,
- read-only report/dashboard/support-bundle evidence can be replayed cold,
- blocked ImagePullBackOff evidence explains itself from a saved bundle,
- uninstall plus host cleanup leaves no active iSCSI sessions or sw-block
  processes.

## Explicit Non-Claims

- Not production-ready.
- No operator lifecycle or CRDs.
- No broad upgrade safety beyond the single gated smoke path.
- No mutating admin UI workflows such as promote, repair, rebuild, failback,
  backup, restore, or delete.
- Cleanup remains scripted/TestOps, not a dashboard button or operator
  workflow.
- No backup, snapshot, or restore workflow.
- No broad distro/kernel/initiator compatibility matrix.
- No performance, RTO, or SLO claim.
- No new recovery semantics beyond previously closed recovery plans.
- No production hosted dashboard; the dashboard is local, read-only, and alpha.

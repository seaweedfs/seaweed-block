Status: beta-candidate note for Phases 41-44. QA passed on 2026-06-17

Release images: **pending publish**. Do not claim this release as shipped until

## Summary

Seaweed Block v0.5 beta candidate adds a bounded Kubernetes lifecycle-owner on
top of the v0.4 status foundation:

```text
SwBlockVolume identity CR created by CSI
protection finalizer added by lifecycle-owner
delete-safety status written by operator-status
cleanup-summary evidence consumed but not executed
unsafe delete evidence holds the finalizer
clean evidence releases only the protection finalizer
Kubernetes Events explain hold/release
report/dashboard/explain show the same delete-safety reasoning
multi-volume delete isolation
zero-residue uninstall verification
```

This is a narrow lifecycle release. It is not automatic cleanup, rebuild,
failback, backup/restore, upgrade execution, or a broad production operator.

## User-Visible Improvements

- A normal CSI `CreateVolume` path can create the matching `SwBlockVolume` CR
  identity object when operator/lifecycle surfaces are enabled.
- The lifecycle-owner can add exactly the Seaweed Block protection finalizer:
  `block.seaweedfs.com/swblockvolume-protection`.
- The lifecycle-owner can remove exactly that finalizer when delete-safety
  status is releasable.
- Kubernetes ValidatingAdmissionPolicy confines lifecycle-owner main-object
  patches to the Seaweed Block protection finalizer shape.
- operator-status remains status/events-only and does not patch finalizers.
- CSI owns `SwBlockVolume` metadata/spec identity and does not write status or
  finalizers.
- Delete requests are held when cleanup evidence is missing, stale, or shows
  residue.
- Clean fresh `cleanup-summary.txt` evidence can mark delete-safety
  `allowed/releasable`, enabling finalizer release.
- CRD status and Events expose hold/release reasons.
- `sw-block ops report`, dashboard `/operator-snapshot.json`, and
  `sw-block ops explain volume --cleanup-summary` can show deleting-volume
  delete-safety reasoning.
- Multi-volume delete state is isolated: one held volume does not contaminate a
  releasable or non-deleting volume.
- Final cleanup verifier remains the authority for zero-residue evidence.

## Current Claim

Seaweed Block v0.5 beta candidate may claim:

- A bounded `SwBlockVolume` protection-finalizer lifecycle is available behind
  the lifecycle-owner chart gate.
- Normal PVC creation can create the `SwBlockVolume` CR identity object when the
  operator/lifecycle surfaces are enabled.
- Delete-safety is evidence-driven:
  - missing/stale cleanup evidence holds,
  - residue evidence holds,
  - clean fresh cleanup evidence releases.
- The lifecycle-owner mutates only the Seaweed Block protection finalizer, with
  Kubernetes admission enforcing the boundary.
- operator-status stays status/events-only.
- CSI owns only the `SwBlockVolume` identity/spec path.
- CRD status, Events, report, dashboard, and explain surface the same
  delete-safety reasoning on the validated paths.
- Multi-volume hold/release behavior is isolated.
- The documented cleanup verifier can prove zero residue after uninstall.

## Explicit Non-Claims

- Not production-ready.
- No automatic cleanup execution.
- No PVC/PV/workload deletion by operator-status or lifecycle-owner.
- No host repair, iSCSI repair, multipath repair, or hostPath repair.
- No promote, repair, rebuild, failback, backup, restore, or cleanup mutation
  through UI/API/operator.
- No upgrade or rollback execution.
- No returned-replica rebuild or automated failback.
- No NVMe ANA parity expansion.
- No production hosted dashboard.
- No performance, RTO, RPO, or SLO claim.
- No broad distro/kernel/cluster compatibility claim.

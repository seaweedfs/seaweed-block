# QA Hard Gate: Light-Use Install And Lifecycle Operations MVP

Status: standing gate. Applies to the active plan
`internal/docs/current-plan.md` ("Light-Use Install And Lifecycle Operations
MVP").

This is QA's hard gate, written from the point of view of an early developer
who has never seen this product before. It sits **on top of** the plan's own
Gates 1-7 (D1-D6). It raises the bar from "boxes checked" to "a real user
would not be confused or stuck."

## Mandate

QA will not sign close based on green CI. QA runs the documented user path by
hand, from a clean state, as a stranger. If any clause below is fuzzy, the
close stops until the doc / scenario / bundle is fixed.

If any single HG clause fails, the close is blocked.

## Gate Clauses

### Step 0 — "Where do I start?"

**HG-0  Single entry point.**
A new user opens the repo or public docs and finds **one** "start here for
Kubernetes" link. That link points at exactly one path. No A/B/C fork before
the user has read a paragraph.

- Fail: the user has to choose between GHCR / local-build / custom-registry
  before they know what those mean.
- Pass: `README.md` (or `docs/overview.md`) carries one "First volume in
  10 minutes" link; the linked page's first command is the one most users
  should run.

### Step 1 — Preflight

**HG-1  Preflight runs, doesn't just inform.**
"Add preflight checks before install" must be a runnable command, not prose.

- Fail: the doc says "make sure `iscsiadm` is installed and kernel modules are
  loaded."
- Pass: `bash scripts/preflight.sh` (or equivalent) emits structured
  PASS/FAIL per check, lists every check it ran in `checked` plus anything
  intentionally skipped in `unchecked`, and exits non-zero on any FAIL with a
  one-line remediation per failed check.

### Step 2 — Install / launch

**HG-2  One command, one happy path, no "also run X."**
The current quickstart contains "Until the operator exists, apply the
blockvolume workload generated by blockmaster: `bash
scripts/apply-k8s-alpha-blockvolumes.sh`". A new user will miss that footnote.

- Fail: the documented happy path requires a side-quest script the user has
  to remember.
- Pass: the single documented command performs every step the demo needs end
  to end, **or** the runbook elevates `apply-k8s-alpha-blockvolumes` into a
  numbered, verified step with its own boundary check (HG-4).

**HG-3  Image fallback is honest.**
Today's doc says "If the GHCR packages are not public yet, use the local
build path below." A new user pasting Option A may hit `ImagePullBackOff`
with no remediation.

- Fail: the doc recommends GHCR without confirming GHCR is publishable today.
- Pass: if GHCR is not public, the default is the local-build path. If GHCR
  is public, the doc names the exact `kubectl describe pod` failure mode the
  user would see if the pull fails, with remediation right next to it.

### Step 3 — Boundary verification

**HG-4  Every boundary has its own command + expected output.**
"Verify every boundary, not just final PASS" cannot be a checklist of state
names.

- Fail: one PASS line at the end. If step 5 of 8 broke, the user has nothing.
- Pass: for each of
  - CSI controller + node pods Ready,
  - StorageClass present,
  - PVC Bound,
  - generated `blockvolume` Deployment Ready,
  - writer pod Succeeded,
  - reader checksum OK,
  - delete returned clean,
  - residue absent,

  the runbook shows the exact command and the exact expected line. A user
  can copy any one of those to debug.

### Step 4 — Failure bundle

**HG-5  Bundle is named and reachable from the runbook, not just from the scenario.**
`sw-block ops status` is built. A user whose `kubectl apply` failed must know
to run it without reading scenario YAML.

- Fail: runbook says "on failure, see internal scenario docs."
- Pass: runbook has an "If something failed" section with the exact
  `sw-block ops status --volume <id> --out <dir>` invocation, **including**
  the case where no volume identity exists yet
  (`ops-status-unavailable: no volume id reached`).

**HG-6  Bundle is self-explanatory to a stranger.**
A maintainer who has never seen this user's lab should be able to read
`volume-status-summary.txt` plus `non_claims` and form a triage hypothesis
without follow-up questions.

- Fail: the bundle's summary needs a cover letter to be useful.
- Pass: QA re-runs Part C-style inspection against a **failing** user-path
  bundle (not the in-test fake) and judges it cold. Pass only if the
  summary + non-claims tell the triage story on their own.

### Step 5 — Cleanup

**HG-7  Cleanup attribution is line-level, not vibes.**
"Cleanup attribution explicit" must be concrete.

- Fail: bundle says `cleanup: ok`.
- Pass: the cleanup summary has one line per resource class, each with
  attribution. Example shape:

  ```text
  pvc:sw-block-demo-pvc                 deleted_by=kubernetes-owner-ref
  blockvolume-deploy:vol-xyz            deleted_by=pvc-owner-ref
  iscsi-session:iqn.2026-05.io.seaweedfs:... released_by=csi-nodeunstage
  host-mount:/var/lib/kubelet/...       cleaned_by=testops-guardrail
  ```

  A reader can immediately see what the product owns vs what the harness did.

**HG-8  Cleanup commands are scoped, not global.**
Today's doc: `kubectl delete deploy -A -l app=sw-blockvolume`. That nukes
every test's blockvolumes across all namespaces.

- Fail: a user with a parallel test loses unrelated state.
- Pass: cleanup commands in the user-facing runbook target only the resources
  this user created, by name or by a per-run label. The `-A` global sweep
  stays in TestOps cleanup, clearly marked as harness-only.

### Step 6 — Idempotency and recovery

**HG-9  Re-run from any partial state.**
A new user will mess up. They will Ctrl-C the script, retry, paste the wrong
YAML, run it twice.

- Fail: second run of the same install command silently mixes state or hangs.
- Pass: the install/launch path is idempotent or fails fast with a "run
  cleanup first" message. QA proves this by hand:
  1. run install, kill it mid-way, re-run;
  2. run install successfully, run again immediately;
  3. run install with a stale PVC of the same name still present.

### Step 7 — Adversarial honesty

**HG-10  At least three real break-classes tested in D6, not one toy.**
D6 says "intentionally break one prerequisite." One is not enough.

- Fail: only the friendly case (bad KUBECONFIG) is tested.
- Pass: QA personally runs at least:
  1. host preflight failure (missing `iscsiadm`),
  2. mid-install failure (wrong image / registry unreachable),
  3. mid-app failure (PVC bound but writer pod cannot mount).

  Each must produce either an `sw-block ops status` bundle that a stranger
  can triage, or the documented `ops-status-unavailable` explanation.

**HG-11  Claims match what was tested.**
The Success Statement is already narrow: "single-node Kubernetes light-use
path." The runbook must not drift.

- Fail: the runbook's final PASS line implies durability or HA.
- Pass: the runbook's non-claims section explicitly lists each disclaimed
  property:
  - pod-local non-durable state,
  - no failover-while-mounted,
  - no multi-node attach,
  - no operator-grade reconciliation,
  - no NVMe-oF in this path,
  - no upgrade / uninstall claim,
  - no performance / SLO claim.

  The success line phrasing makes none of those by accident.

### Step 8 — Runbook vs scenario consistency

**HG-12  D1 runbook and D2 scenario do the same thing, observably.**
A user who copies the manual commands from D1 should end up in a state
indistinguishable from a clean D2 scenario run.

- Fail: the scenario uses a label/name the runbook does not mention; the
  runbook does a step the scenario skips.
- Pass: QA diffs a D1 manual run against a D2 scenario run; the only
  differences are timestamps and run-id. Same resource names or same label
  scheme, same artifact layout, same final cleanup attribution.

## QA Process Commitment

- Validation host: m02 (`192.168.1.184`) k3s lab, or a user-provided
  equivalent single-node Kubernetes lab that passes
  `docs/quickstart-kubernetes.md` preflight.
- QA does not sign off on close based on "all gates green in CI." QA runs
  the documented runbook by hand, cold, from a clean state on the supported
  lab shape (m02 + k3s, or M01 + k3s), as a user who has not seen the dev
  process. If QA gets confused, close stops until the doc is fixed.
- QA deliberately breaks at least the three break-classes in HG-10 and
  rejects the close if any break produces a bundle that does not help.
- QA reports findings against this gate in the close report. Any HG-clause
  failure must be quoted verbatim in the verdict.

## Required Break Fixtures For HG-10

QA should use concrete break fixtures, not friendly synthetic errors:

1. Host preflight failure: temporarily hide or shadow `iscsiadm` for the
   preflight process, or run on an equivalent node without `open-iscsi`.
2. Mid-install image failure: set `SW_BLOCK_IMAGE` or `SW_BLOCK_CSI_IMAGE` to a
   registry/tag that the cluster cannot pull, then confirm the runbook names
   `ImagePullBackOff` and points to remediation.
3. Mid-app attach failure: interrupt the generated blockvolume readiness path
   after PVC creation but before writer success, for example by scaling or
   deleting the generated blockvolume Deployment during the run, then confirm
   the artifact bundle identifies the boundary.

Each break must produce either a useful `sw-block ops status` bundle or the
documented `ops-status-unavailable` explanation.

## Open Adjustments

If any HG clause is judged too strict for alpha, it must be downgraded
**before** dev starts D1-D6, not at close time. Late downgrades are not
accepted: that is the failure mode this gate exists to prevent.

## Non-Claims For This Gate

This gate validates the **user-facing operational loop** on the supported
single-node shape. It does not validate:

- production HA,
- performance,
- multi-node attach,
- operator-grade reconciliation,
- upgrade / uninstall,
- UI / dashboard,
- mutating admin / repair controls.

Those remain non-claims of the active plan; this gate does not silently
extend them.

# QA Pre-Release - v0.3 User Walkthrough Blockers

Date: 2026-05-22

Verdict: PRE-RELEASE BLOCKERS found during walkthrough. Fixes landed after
this report; see "Resolution Update" below. The original v0.3 testops gates PASS
(`20260522-031019-ef25`, `20260522-031124-0a44`) but exercise
`scripts/generate-helm-values-day1.sh`, NOT the user-facing command
`sw-block ops generate-helm-values` advertised in `README.md` and
`docs/quickstart-kubernetes.md`. A fresh end-user following the documented
quickstart literally on a 3-node k3s lab (m01 / m02 / tp01) cannot complete the
first-volume loop.

## Method

- Start state: clean k3s cluster, no `sw-block` PATH binary, no prior install,
  no iSCSI sessions, no multipath maps.
- Followed `docs/quickstart-kubernetes.md` from Step 1 verbatim.
- Re-ran from clean state with the workaround applied.

## Blockers

### B1. `sw-block` is not in PATH and the docs do not say how to build it

Reproduce:

```bash
sw-block ops generate-helm-values --out values.day1.yaml
# bash: sw-block: command not found
```

`docs/quickstart-kubernetes.md` Prerequisites line 43 mentions the `go run`
fallback, but no doc tells a user to `go build -o sw-block ./cmd/sw-block`.
Every fresh user hits this on the first documented command.

Fix shape:

- Add Step 0 to `docs/quickstart-kubernetes.md`:
  ```bash
  git clone https://github.com/seaweedfs/seaweed-block && cd seaweed-block
  go build -o sw-block ./cmd/sw-block && export PATH="$PWD:$PATH"
  ```
- Mirror the same step in `README.md` Quick Start Fast Path.
- Confirm `sw-block --version` prints a real revision when built this way
  (current `go run` output is `revision=unknown modified=unknown`).

### B2. Default `:alpha` GHCR image is incompatible with v0.3 chart

Reproduce:

```bash
sw-block ops generate-helm-values --out values.day1.yaml
helm install sw-block charts/seaweed-block \
  --namespace kube-system --create-namespace \
  -f values.day1.yaml --wait
# Error: INSTALLATION FAILED: context deadline exceeded   (5 min)
# blockmaster CrashLoopBackOff: flag provided but not defined: -launcher-replication-ack
```

`charts/seaweed-block/templates/blockmaster.yaml:48` emits
`--launcher-replication-ack={{ .Values.replication.ackProfile }}`
unconditionally. The published `:alpha` GHCR tag predates this flag.
Compare with `--launcher-reject-loopback-publish-targets`, which IS gated
behind `compat.launcherRejectLoopbackFlag`.

Fix shape (pick one):

- Add a `compat.launcherReplicationAckFlag` knob, default `false` for
  alpha-tag compatibility, true when running fresh SHAs.
- Republish `:alpha` to a current commit that supports the flag and document
  the publish cadence so users know the floor.
- Document the current working immutable SHA in `docs/releases/v0.3-alpha.md`
  and have `generate-helm-values` default to that pinned SHA.

The doc currently says "Mutable `:alpha` is a smoke/demo tag only" but never
names a working SHA; a user has to grep the testops scenario YAML to find
`sha-28a99ce4f644`.

### B3. `sw-block ops generate-helm-values` produces broken port assignment

This is the most severe finding. With B2 worked around (`--image sha-...`),
the install succeeds — but the launcher-generated blockvolume pod still
CrashLoopBackOff on the primary node:

```text
blockvolume: iscsi target: iscsi: listen "192.168.1.181:3260":
  bind: address already in use
```

Root cause: `cmd/sw-block/main.go:974` assigns

```go
DataPort: 3260 + i,
```

so node[0] = m01 gets `dataPort: 3260`, which is identical to the iSCSI
listener port (also 3260 from the launcher `--iscsi-port-base`). The
blockvolume pod opens two listeners on the same `host:port` and the second
bind fails.

`scripts/generate-helm-values-day1.sh:221-222` assigns:

```bash
data_port=$((19101 + (idx * 2)))
ctrl_port=$((data_port + 1))
```

19101+ does not collide. **The QA-passing testops scenarios use this shell
script; the documented user-facing `sw-block ops generate-helm-values` does
not match it.**

Reproduces both times from clean state on the 3-node lab. Writer pod stuck in
`ContainerCreating`, PVC event:
`AttachVolume.Attach failed ... has no publish target`.

Fix shape (pick one):

- Align `cmd/sw-block/main.go:974` with the shell script's port scheme
  (`dataPort = 19101 + 2*i`, `controlPort = dataPort + 1`).
- Or flip the docs to call `scripts/generate-helm-values-day1.sh` (matches
  what QA actually validates).

Pick (a) unless the long-term intent is to retire the Go path.

### B4. Documented `helm install ... --wait` (no `--timeout`) hits 5-min default

Reproduce: the literal command timed out at exactly 5m0s with
`context deadline exceeded`. The 5 min was actually masking blocker B2 above,
but even on cold image pulls a 5-min default is tight.

Fix shape: add `--timeout 10m` to every documented `helm install --wait`
invocation:

- `README.md` Fast path (line ~119)
- `docs/quickstart-kubernetes.md` Step 2 (line ~119)
- `docs/releases/v0.3-alpha.md` Validated User Path (line ~54)

## Medium / discoverability

### M1. `sw-block ops` usage banner omits `dashboard`

```bash
go run ./cmd/sw-block ops
# usage: sw-block ops status|inventory|cluster|volumes|describe|timeline|
#                  explain|report|generate-helm-values
```

But README and quickstart both document `sw-block ops dashboard`. Banner is
out of sync with the binary's actual surface.

### M2. `--from-bundle "$APP_DIR"` vs `$APP_DIR/status` is ambiguous

Quickstart Step 4 passes `$APP_DIR` (the basic-app dir) to
`sw-block ops dashboard --from-bundle`, but the report files live under
`$APP_DIR/status/report/`. Worth one sentence in the doc explicitly stating
the bundle root.

### M3. Magic positional `"$PWD"` to helper scripts

Three documented invocations:

- `bash scripts/run-basic-app-example.sh "$PWD"`
- `bash scripts/activate-k8s-alpha.sh "$PWD"`
- (implied repo root elsewhere)

No doc explains what the positional argument means. New users see undocumented
magic.

### M4. KUBECONFIG fallback is k3s-specific

`docs/quickstart-kubernetes.md` Step 1:

```bash
export KUBECONFIG="${KUBECONFIG:-/etc/rancher/k3s/k3s.yaml}"
```

is a no-op for non-k3s users with KUBECONFIG already set and a bad fallback
for non-k3s users without it. Should comment "k3s default path; non-k3s users
keep your existing KUBECONFIG."

Note: vanilla k3s ships `k3s.yaml` mode 600 (root only). On supported labs
`--write-kubeconfig-mode 644` is used. Doc should warn fresh k3s users.

### M5. v0.3 release notes mention `sha-<commit>` images but name no working SHA

`docs/releases/v0.3-alpha.md` Image Guidance says to use immutable
`sha-<commit>` for QA/PM/release validation but does not name which commit is
current. User has to grep `testops/scenarios/helm-first-volume-chain.yaml` to
find `sha-28a99ce4f644`.

## Gap in QA Coverage

The v0.3 close report verdict ("PASS strict") is honest for the scenarios it
ran, but the testops gates cover the **shell script path**, not the
**documented `sw-block ops generate-helm-values` Go path**. B3 is a real
release-blocker that is invisible to the existing QA gates.

Fix shape:

- Add a testops scenario (e.g.
  `testops/scenarios/helm-first-volume-via-sw-block-cli-chain.yaml`) that
  invokes `sw-block ops generate-helm-values` directly with no shell-script
  fallback. Treat it as a zero-regression gate for v0.4+.
- Until that scenario exists and passes, the documented user path should not
  be claimed to work on a fresh cluster.

## Recommended Sequence

1. B3 first (port assignment) — single-file fix in `cmd/sw-block/main.go`,
   unblocks the documented user flow.
2. B2 second (chart-vs-image flag gate) — keeps `:alpha` viable for casual
   try-it-out users.
3. B1 + B4 (Step 0 + `--timeout 10m`) — pure doc edits.
4. M1-M5 — opportunistic.
5. Add Go-path testops scenario before claiming v0.4 release-ready.

## Resolution Update

Resolved on 2026-05-22 after this blocker report:

- B1: README/quickstart now include a Step 0 / fast-path CLI build:
  `go build -o sw-block ./cmd/sw-block && export PATH="$PWD:$PATH"`.
- B2: Helm chart now gates `--launcher-replication-ack` behind
  `compat.launcherReplicationAckFlag`, default false, and docs use the
  validated immutable image tag for the v0.3 walkthrough.
- B3: `sw-block ops generate-helm-values` now uses the same non-conflicting
  per-node data/control port scheme as the shell generator:
  `19101/19102`, `19103/19104`, `19105/19106`, ...
- B4: README, quickstart, and v0.3 release note now use
  `helm install --wait --timeout 10m`.
- M1: usage output includes `dashboard`.
- M2-M5: docs now clarify bundle root, `"$PWD"` helper argument, k3s
  `KUBECONFIG` fallback, and current validated immutable image tag.

New zero-regression gate:

- `testops/scenarios/helm-first-volume-via-sw-block-cli-chain.yaml`
- Run `20260522-091642-b9a7`
- Result: PASS, 31/31 actions
- The gate builds `sw-block`, invokes `sw-block ops generate-helm-values`
  directly, asserts `dataPort: 19101`, asserts no `dataPort: 3260`, installs
  Helm, verifies writer/reader, and checks cleanup.
